# Research record and contribution

Research began before substantial implementation on 2026-09-24. The supplied request was the specification; no separately attached architecture document was available. The surveys below record primary-source inspection of repositories, licenses, release listings, source code and protocol documents. Their decisions are engineering choices for this prototype, not rankings of project quality.

## What is existing technology

A2A supplies agent-card/interoperability schemas. MCP supplies tool discovery and invocation semantics. OpenTelemetry supplies trace transport and a developing GenAI vocabulary. Kubernetes, Docker and registries supply infrastructure inventory. Open-source agent frameworks expose trace processors, event listeners and hooks. Workload identity systems such as SPIFFE/SPIRE and existing governance toolkits already address identity and inventory reconciliation. None of these ideas is claimed as newly invented here.

## What this implementation adds

The original components join these sources into one evidence-preserving pipeline: normalized candidates, bounded behavioral fingerprints, conservative agent gates, explicit identity merge decisions, declared/observed/inferred capabilities, a relational knowledge graph, an inventory that retains non-agent entities, shadow review reports, and policy-filtered matching/routing. The offline environment exercises the whole path with synthetic peers and measured results.

The classifier, closed tool-to-capability dictionary, lexical task analyzer and identity rules are proposed experimental mechanisms. They are deterministic and explainable, not learned or statistically calibrated. Unknown fields remain unknown. A card, framework import, LLM call or MCP inventory by itself is insufficient to establish agent behavior. Telemetry remains an attributed claim unless a separate trust mechanism verifies its producer.

The existing Microsoft Agent Governance Toolkit discovery component is especially relevant prior art: it already reconciles discoveries with registrations. This project's contribution is the specific integration and evaluated local policy, not invention of agent discovery or shadow-agent detection. The source survey found no verified drop-in component satisfying the entire requested combination; this limited result is not a claim that none exists anywhere.

## Implemented profile versus future work

The final support matrix is [protocols](protocols.md) and [discovery sources](discovery-sources.md). It takes precedence over research recommendations below. The implementation has bounded A2A/MCP profiles and generic metadata imports; it does not claim complete latest-protocol interoperability. OTLP ingress supports a documented JSON subset, not gRPC/protobuf collection or universal automatic instrumentation. No real OpenAI, Anthropic, LangGraph, CrewAI or AutoGen deployment was executed: their inspected exporter/hook surfaces are integration guidance, not validated installed integrations.

The request mentions ARD-compatible metadata without a versioned normative ARD specification. Generic registry metadata is supported, but no invented ARD wire protocol or conformance claim is made. Production attestation, OAuth, signature validation, complete SDK transport support and learned semantic routing remain future integrations.

## Evaluation and research limits

See [evaluation](evaluation.md) for formulas, sample sizes, measurements and reproduction commands. The small synthetic fixture set validates a mechanism and catches regressions; it cannot establish enterprise-wide coverage, robustness to adversarial telemetry or a production false-positive rate. Better research would add independently labeled workloads, difficult static-workflow negatives, held-out framework versions, temporal ownership changes, cross-tenant identity cases, spoofed telemetry, calibration curves and repeated load experiments.

Dependencies are reused through pinned Python distributions, with no copied upstream implementation files or vendored repository. Their version/license inventory appears in [open-source components](open-source-components.md). The following research notes are the preimplementation record, including alternatives rejected for this prototype. Source links to `main` are mutable; their stated releases are research snapshots, not dependency pins.

### A2A interoperability constraints

The current [A2A specification](https://a2a-protocol.org/latest/specification/) uses `/.well-known/agent-card.json`. Cards contain ordered `supportedInterfaces`; select the first compatible entry, use its URL, binding and protocol version, and copy its optional tenant into requests. Standard bindings are `JSONRPC`, `HTTP+JSON`, and `GRPC`. Version requests use major.minor (such as `1.0`) in `A2A-Version`; absent version implies 0.3. This makes silent schema mixing unsafe. Preserve the original document alongside normalized fields and report the detected profile.

Current [proto definitions](https://github.com/a2aproject/A2A/blob/main/specification/a2a.proto) require card name, description, supported interfaces, agent version, capabilities, default input/output modes and skills. `capabilities.extendedAgentCard` indicates optional authenticated details. Skills contain id/name/description/tags and optional media modes/security. `securityRequirements` uses a `schemes` map whose values hold `list` scope arrays. Security-scheme objects are wrapped by their concrete type. Agent version is distinct from protocol version. Cards describe capabilities; they do not prove they are available or safe.

The inspected [Python resolver](https://github.com/a2aproject/a2a-python/blob/main/src/a2a/client/card_resolver.py) converts legacy `url`, `preferredTransport`, `additionalInterfaces`, `protocolVersion` and `security` into newer forms. A local importer can normalize these deliberately while retaining raw evidence. Signature presence must remain separate from signature verification. Apply network authorization, HTTPS verification, URL/redirect controls and body/time limits before fetching any advertised URL. Never automatically fetch authenticated extended cards or execute agent tasks merely because discovery found them. These last controls are architecture recommendations.

### MCP interoperability constraints

There are two materially different protocol eras. The [2025-11-25 lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle) requires `initialize` first (version, client info, capabilities), followed by `notifications/initialized`. A bounded adapter using this flow must advertise that exact supported profile and validate the returned negotiated version before listing tools.

The [2026-07-28 versioning specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) replaces required initialization with per-request metadata. An unsupported version returns JSON-RPC error `-32022` with supported versions. A recognized modern protocol error must not trigger legacy fallback. [server/discover](https://modelcontextprotocol.io/specification/2026-07-28/server/discover) is required on modern servers, optional as client preflight, and reports `supportedVersions`, `capabilities`, `resultType: complete`, and display identity. Request `_meta` contains `io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientInfo`, and `io.modelcontextprotocol/clientCapabilities`. Display server identity is not authenticated identity.

Modern [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) uses individual POST requests, JSON or request-scoped SSE replies, and no protocol sessions or standalone GET stream. Send `Accept: application/json, text/event-stream`; include `MCP-Protocol-Version` and `Mcp-Method`, plus `Mcp-Name` for named methods. Body/header mismatches are rejected with HTTP 400 and error `-32020`. Origin validation is required on servers. Full clients must handle `x-mcp-header` annotations and safe header encoding. A JSON-only probe that rejects SSE is a documented partial profile, not a complete MCP client.

[Tools discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) uses `tools/list` and cursor pagination. Store descriptions and JSON schemas as untrusted descriptive metadata. Retain input/output schema and annotations; follow `nextCursor` with page/size limits. Modern results may include `ttlMs` and `cacheScope`; auth-dependent inventories must not be shared across principals. Introspection must never call `tools/call`, install packages or launch stdio commands as a discovery side effect. These execution boundaries are architecture recommendations.

For protected HTTP MCP, [authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) uses OAuth 2.1 resource-server semantics and Protected Resource Metadata. Clients request resource-specific tokens; servers validate intended audience. Authorization belongs on every request, never in URI query parameters. Invalid tokens receive 401, insufficient permissions 403. Do not forward arbitrary inbound bearer tokens to discovered endpoints. Registry ownership, OAuth identity and observed transport health are separate trust attributes.

### Registry, Kubernetes and identity mapping

The [generic registry API](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/generic-registry-api.md) exposes `/v0.1/servers`, version listings and `/v0.1/servers/{serverName}/versions/latest`; URL-encode the slash-bearing server name. The [official extension](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/official-registry-api.md) supports `updated_since`, simple name `search`, and `version=latest`. Publication uses namespace ownership authentication. Import remote URLs and package descriptors separately; package-only entries are discoverable records without an HTTP runtime. Never treat a registry record as proof of liveness.

[EndpointSlice documentation](https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/) identifies services using `kubernetes.io/service-name` and endpoints using address type, addresses, port and conditions. `ready` normally combines serving and non-terminating, but `publishNotReadyAddresses` alters that meaning. Design a namespaced, opt-in label/annotation collector with list/watch RBAC only, resourceVersion recovery and UID-based identity. A Kubernetes service is only an agent candidate until metadata identifies A2A/MCP or an approved annotation supplies its manifest. Snapshot imports cannot claim live cluster collection.

[SPIFFE overview](https://spiffe.io/docs/latest/spiffe-about/overview/) distinguishes workload identifiers from SVID credentials and trust domains. Recommended catalog fields: claimed identity, verified identity, verification mechanism, trust domain, evidence source, verification timestamp and expiry. Attestation may link an endpoint to a workload; authorization still needs application policy. Avoid conflating a friendly name, DNS name, Kubernetes label, registry publisher and cryptographically verified principal.

### Prototype recommendation

Keep the initial catalog protocol-neutral with raw evidence, source-specific external IDs, normalized endpoints/capabilities, trust state, last-seen/expiry, and explicit adapter-profile versions. Implement only authorized discovery. A2A card import and registry metadata import are simpler than complete protocol clients. Use fixture/snapshot import for Kubernetes until a real cluster connection is configured. Provide fail-closed network constraints and clear unsupported-profile diagnostics. Adopt official SDKs when moving from bounded inspection to execution or complete SSE/modern protocol support; do not silently advertise interoperability that has not been tested.

### Practical findings

#### Shadow-agent detection is not a blank field

Existing open-source inventory/reconciliation implementations exist, including Microsoft's toolkit above. The inspected implementation explicitly includes process/config/GitHub discovery and registration reconciliation. It therefore would be incorrect to claim that this prototype invented discovery or unregistered-agent identification.

The inspected reconciler accepts a registered name as a substring match, and unmatched observations receive shadow status. This is an implementation observation from the source, not a blanket assessment of the toolkit's current versions. The current task needs more conservative identity rules, retention of separate non-agent entities, evidence of autonomous behavior, and careful treatment of MCP servers. Thus we did not find a ready-made, verified component in this survey that can be dropped in to satisfy the entire requested behavioral-classification/cross-source-identity/capability-routing pipeline. That limited conclusion is not evidence that no such project exists anywhere.

Additional query triage found [PatronAI](https://github.com/giggsoinc/patronai), whose README describes network-provider matching and code import scanning (Apache-2.0), and [Shadow AI Governance Detection](https://github.com/zerokali20/Shadow-AI-Governance-Detection), whose README describes approved-tool and payload-risk checks (MIT, four commits displayed). These were **REJECTED at README triage**, not source-audited: their useful signal is AI use, whereas the prototype must distinguish tool servers, wrappers, and services from agents. No claims about their classifier implementation or deployment quality are made. No code was copied. [ShadowLens](https://github.com/iamsparshgupta/shadowlens) was **REJECTED at license triage** because its README specifies proprietary/all-rights-reserved terms; its browser-extension usage detection also differs from this task. These triage results are not dependencies.

#### Recommended telemetry contract

1. Accept an explicitly documented OTLP/HTTP **JSON traces subset** plus the project's normalized event envelope. Do not label a custom event endpoint a complete OTel collector. The common Python OTLP exporter defaults to protobuf, so it will need a supported collector/export conversion or the documented JSON ingestion path; do not advertise direct compatibility without testing it.
2. Parse `resourceSpans -> scopeSpans -> spans`, resource `service.name`, service namespace/instance identifiers when present, trace/span/parent identifiers, timestamp, and selected `gen_ai.*` attributes.
3. Translate inference operations (`chat`, `generate_content`, `text_completion`) into `llm_call`, `execute_tool` into `tool_call`, and `invoke_agent` into `agent_call`. Preserve `invoke_workflow` as workflow evidence. Do not equate a workflow or agent invocation span with autonomous behavior by itself.
4. Planning, delegation, memory access and autonomous action must come from explicit observed events or supported semantic attributes. If unavailable, leave them unknown. A tool name or prompt text is insufficient to invent these facts.
5. Store a source-qualified event identifier and deduplicate by source/trace/span so replay cannot inflate confidence. Prefer a bounded observation window over permanent accumulation of unrelated weak signals.
6. Include the trust boundary: telemetry supplied by a service is a claim. An authenticated collector establishes the sender, not the truth of every attribute. Mark provenance and distinguish registered identity from cryptographically verified identity.
7. Record only allowlisted metadata required for classification. Do not store raw prompts, model outputs, tool arguments, HTTP authorization headers, environment dumps or configuration secrets.

The [OpenTelemetry agent convention](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md) is still in Development. Its new dedicated repository and [migration notice](https://github.com/open-telemetry/semantic-conventions/blob/main/docs/registry/attributes/gen-ai.md) should be named in documentation; the prototype must not claim a frozen stable GenAI standard.

#### Framework compatibility boundary

The offline demo should require no LangGraph, CrewAI, AutoGen, OpenAI or Claude runtime and make no real LLM calls. Synthetic fixtures may identify these frameworks, but that is not a tested integration with the framework itself. Document application-side integration recipes separately, with the trace processor/event listener/hook surfaces above. Only list a framework integration as implemented once its exporter and contract have executable tests.

#### Capability matching and graph boundary

Keep capability provenance separate: declared card skill, observed successful tool invocation, and inferred capability from a documented mapping. Unsupported task text should produce no match, rather than defaulting to a popular agent. Apply trust, endpoint authorization, health, protocol, and tenant constraints before execution. Preserve the exact evidence that contributed to the score.

A directed relational node/edge representation is enough for the required graph view and per-agent relationships. Framework execution graphs such as LangGraph are not substitutes for an inventory knowledge graph. A relation such as `DELEGATES_TO` should retain the runtime observation that produced it; graph edges must not invent owners or dependencies.
