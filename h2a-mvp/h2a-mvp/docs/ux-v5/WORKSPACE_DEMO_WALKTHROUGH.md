# H2A Work Workspace: Screen-by-Screen Walkthrough

Date: 2026-09-06
Scope: Newly integrated local-operator workspace, not final enterprise acceptance.

Current startup now requires employee sign-in. Verify your registered Employee ID, then choose **Administrator console** before following the retained gallery walkthrough below. Staff cannot access that console. See [Employee Access and Memory](EMPLOYEE_ACCESS_AND_MEMORY.md) for named room membership, reviewed Memory, exact-scope credential renewal and current limitations. No remote-stop demonstration is valid until the receiver containment protocol is implemented.

## Before Recording

- Use the intended existing H2A data root. Do not replace it with a test-only screenshot root or create synthetic acceptance records.
- Confirm the actual employees, credentials, provider sessions, mandates and grants are current. Respect revoked authority; renew only through the permitted explicit workflow.
- Use real nonproduction work and approved repository paths. Provider login/consent and physical-person verification remain operator actions.
- Required liveness must be genuinely passed before claiming liveness-backed verification. Photos/demo bypass do not satisfy that claim.
- This workspace is a trusted local-operator view. It is not yet a CISO-versus-finance-versus-engineering read-isolated portal.

## 1. Enter And Meet The Team

1. Start H2A with the same known data root.
2. Click **Open Work workspace** in the existing Office/Control screen.
3. Click **People & agents**.
4. Show each employee's actual name, department, roles and registered agents. An unresolved remote owner stays an ID, not a invented employee profile.
5. Select **Authority** at the top to expose more scope detail. Select **Proof** to expose the actual Human, Membership, Agent, Passport and Session references.
6. **Manage people**, **Add agent**, and **Connect coworker** open the existing connected controls in place. These setup forms have not all been redesigned into short wizards.
7. Close the panel with its close icon or Escape. The named Human Proof dialog remains separate and must identify the correct person and exact purpose.

Say: "These are accountable owners and their workload identities. A provider being available for planning does not mean it has already executed this task."

## 2. Create Real Work

1. Click **Work**, then **Start something**.
2. Enter the clothing-site objective in **What should the team accomplish?**
3. Choose the real **Accountable person** and **Project**. If no project exists, use **Register a project** and register an approved local Git root through the existing form.
4. Enter **Expected results, one per line**, such as a reviewed design, working code and validation receipts. Enter real limits in **Limits & requirements**.
5. Choose **Sensitivity** and an optional **Deadline**.
6. Click **Review the plan**. This saves a goal and invokes the existing planner. A planning error does not erase the saved goal.
7. In the room, click **Plan** and inspect the proposed steps, owners, dependencies and allowed paths. The current planner is deterministic; do not present this as a model having autonomously researched or reasoned out the plan.
8. Before approval, **Edit plan** opens the editor for this exact goal. Use each step's **Agent** and **Depends on** selectors, then **Save edits**. Close the panel and inspect the updated revision.
9. Click **Approve this plan**. Complete the requested exact-purpose Human Proof for the named person. If verification was required, click **Approve this plan** again after the host updates. Approval is not automatic provider execution.

## 3. Show The Agent Room

1. Click **Room**. Each tile represents an assignment, with its provider, accountable owner and actual state. One agent can have multiple assignments.
2. Click an agent avatar to focus its tile; click it again to **Return to gallery**.
3. Hover the triangular Run icon on a permitted assignment. Click to run that assignment only.
4. Start independent eligible steps without implying that visual tile order is a required sequence. Dependency-bound steps remain blocked until their real predecessors succeed.
5. Wait for host-persisted changes. If an operation fails, inspect its real error; do not narrate it as success.
6. Use **Plan** to see what is waiting and **Outputs** to see recorded result references.

Say: "This is a meeting-style view of agent work, not a video call, simulated agent conversation, or invented presence feed."

## 4. Explain Bounded Context

1. Click **Context**.
2. Show each assignment's **Permitted fields** and **Kept back** list. These describe planned scope, not successful delivery.
3. Below, show actual **Disclosure receipts** for matching assignment, grant, recipient agent and Passport.
4. Explain the released field transformations, such as value, mask, summarize or reference. The source values themselves are not displayed here.
5. Select **Proof** and inspect the receipt, projection hash and decision. Use its inspection arrow to open the evidence panel.
6. Use **Manage sharing** only for an intentional scope action. Room participation never grants access to another owner's private context.

Do not call this shared model training or automatic company learning. **Memory** explicitly remains unavailable until reviewed publishing, retrieval and revocation are implemented.

## 5. Independent Decisions And Results

1. Click **Decisions** to inspect the exact plan approval and any real approval checkpoints.
2. Click **Review approvals** to open the existing Authority Inbox.
3. Select the actual pending protected request. Have the different eligible employee verify the displayed exact purpose and approve or reject the request.
4. Use the existing **Resume once** control only for a valid approved paused effect. Retain the persisted outcome and verify no duplicate effect.
5. Return to **Outputs**. Inspect actual hashes and validation references, not just provider connectivity.
6. Use **Review project changes** to open the existing integration controls. Integrate only the independently accepted result through the real workflow.

An empty Decisions or Outputs view is not completed acceptance. A remote acknowledgement is not sufficient proof of remote provider work.

## 6. Containment And Audit

1. On a separate disposable assignment, start a genuine operation.
2. While it is actually running, use its square **Cancel** icon. Check the resulting terminal state and evidence.
3. For local mandate revocation, use the shield-off **Withdraw permission** icon. Read the confirmation: the mandate and descendants are affected, existing evidence remains, and this is not undone by refreshing.
4. Complete exact-purpose verification if requested, then confirm withdrawal. Wait for the canonical revoked state and inspect containment evidence.
5. The new workspace does not expose remote mandate withdrawal as a guaranteed remote stop. That transport/receipt path still needs implementation and acceptance; do not substitute a local event for remote containment.
6. Select **Proof**, then **Reconstruct this work**. Follow the actual trace and identities, mandates, context receipts, decisions and output references.
7. Restart with the same data root. Reopen the task and compare the recorded IDs, hashes and terminal receipts.

## 7. What To Claim And What Not To Claim

| Demonstrable when supported by actual receipts | Not established by this UI integration |
| --- | --- |
| One durable task across gallery, plan, context, decisions and outputs | Department-specific authenticated read isolation |
| Human-owned workload identity and scoped assignment references | Durable room admission, lending or live multi-person presence |
| Real provider work through installed existing adapters | Universal control over every tool or every external agent |
| Exact-scope approval and independent protected-action decisions | Automatic approval because a person entered a room |
| Scoped disclosures and minimized evidence | Automatic learning from private room content |
| Local cancellation/revocation when verified against real processes | Remote revocation enforcement based only on a local event |

Use **Readiness & receipts** for the existing acceptance controls. All carried operator checks and full release verification still apply. To return to Office/Control, go to **Work**, select **Proof**, and click **Open engineering console**.
